01 · Purpose

LLM calls are expensive, slow, non-deterministic, and opaque. InferenceLens makes them operable: the chat app supplies real traffic, and the pipeline turns every call into a record you can debug, price, and aggregate.

Debugging

When a user reports a bad answer, the log shows exactly what the model was sent and what it returned — the single highest-value query in observability systems.

Cost & attribution

Tokens are money. Per-call cost_usd is stamped at ingestion from a versioned price map, so historical costs stay correct when prices change.

Latency & reliability

p50/p95/p99 latency, time-to-first-token, error rates, per-model breakdowns — the on-call surface for an LLM product.

02 · Chat interface

Deliberately small — its job is to generate real inference traffic. Still built properly:

  • Multi-provider, multi-model. OpenAI and Anthropic behind one ChatProvider interface; the model is selectable per message from a GET /models catalog. Adding a model is a one-line change.
  • Streaming responses. Replies stream over SSE, and streamed calls record time-to-first-token into their logs.
  • Persistent conversations. List by recency, reopen any conversation and continue it — the model gets a sliding window of history, and titles are auto-generated in the background (itself a logged call).
  • Typed at every boundary. Pydantic schemas on every request and response; no raw dicts cross the API.

03 · Logging pipeline

A portable SDK (app/logging_sdk/) that imports nothing from the application — config arrives as constructor arguments, provider knowledge through an ABC. It could be lifted into another codebase unchanged.

One call, one event — the emission chain

provider.send_message(…)ordinary call site — no logging imports
LoggingChatProviderdecorator — the only provider ever handed out
CallRecorder.invoke()single emission point · times the call · asks the adapter to describe_call / outcome / failure
every exit path: success, error, cancel
InferenceLogEventversioned contract · schema_version=1 · request_id
EVENT_PROCESSORSPII redaction (scrubadub) — fails open per field
fire-and-forget — never awaited, never raises
EventPublisherinterface · HTTP or Kafka, chosen at startup

A publish failure produces an ERROR line and a lost event — never a failed or slowed chat request. Observability must never take down the thing it observes.

Structural, not optional

Concrete adapters aren't exported; get_chat_provider() always returns the instrumented decorator. An unlogged call path doesn't exist to forget about.

Provider-agnostic

The SDK never reads a vendor response. Adapters self-describe through three abstract methods; vendor quirks stop at the adapter boundary.

Technologies

Pydantic v2 events · httpx (HTTP transport) · aiokafka (Kafka transport) · scrubadub (redaction). Nothing else.

The validating gate between events and storage. Its contract is the event payload alone — it knows nothing about the chat schema, which is what lets it move to its own service later.

Kafka mode commits offsets only after the DB commit; a crash in between redelivers the batch and every row dedups on request_id — at-least-once delivery, effectively exactly-once storage.

Why validate here

Malformed payloads get a 422 (HTTP) or are logged and skipped with offset context (Kafka) — bad events never poison the store or crash the loop.

Why cost here

Stamped once, at write time. The log is immutable; recomputing cost at read time would silently rewrite history whenever prices change.

Why idempotent

A UNIQUE constraint on request_id, not an application-level check — it holds under concurrency and makes redelivery free.

05 · Extensibility & developer experience

The whole developer experience of making a logged LLM call: 

provider: ChatProvider = Depends(get_chat_provider)   # already instrumented
result = await provider.send_message(messages, model=..., max_tokens=...)
# that's it — the log exists. No logging imports, no wrapper to remember.

Everything that's expected to change sits behind an interface, and each change has a known blast radius:

Add a provider

TouchOne adapter file — the ABC forces describe_call/outcome/failure, so a missing mapping is a TypeError, not a silent log gap
UntouchedSDK, event schema, ingestion, log table

Add a model

TouchOne line in MODEL_CATALOG + a price-map entry
UntouchedGET /models, selection, cost — all pick it up

Add a transport

TouchOne EventPublisher implementation + one branch in the composition root
UntouchedEvery call site — this is exactly how Kafka landed

Add an event processor

TouchOne function appended to EVENT_PROCESSORS
UntouchedEverything else — redaction ships this way today

Modular by layer

Routers (HTTP) → repositories (SQL) → models. Providers, SDK, and ingestion are separate packages with one-way dependencies.

Portable SDK

grep "from app\." app/logging_sdk/ returns nothing — the boundary is a one-line mechanical check in review.

Config over code

EVENT_TRANSPORT, ANALYTICS_ENGINE, DATABASE_URL — transports, engines, and stores swap in .env, not in source.

06 · Future considerations

Sized for the scale it runs at; grown by swapping, not rewriting. Two evolution paths are already one step in:

Storage

Transport

HTTP fire-and-forget
zero-infra default
Kafkanow
durable, replayable, opt-in
Multi-consumer fan-out
alerting · evals · rollups

Multi-tenancy

Auth + a nullable user_id through the event schema — an additive migration. Per-tenant cost attribution falls out of existing columns.

Tracing

A trace_id grouping one user action's calls (tool use, retrieval). OTel-aligned naming makes an exporter straightforward.

Quality scores

An inference_scores table written by LLM-as-judge and user-feedback pipelines — enabled by full content already being stored.

Retention

TTL deletion plus cold-storage offload of content columns — tiered storage, the standard answer to unbounded log growth.

Pipeline hardening

Dead-letter topic for malformed messages; SDK-side bounded queue with batch flush and drop-on-overflow.

Real-time aggregation

A stream processor only if windowed alerting becomes a requirement — SQL rollups cover everything before that.
